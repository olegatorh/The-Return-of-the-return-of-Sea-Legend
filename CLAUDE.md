# CLAUDE.md — start here (for AI assistants and new contributors)

## What this project is
A **re-implementation of the Storm Engine** (Akella, 2003) in **Godot 4 (C#)**, so that the old game *Pirates of the Caribbean / Sea Dogs 2* with the addon
**"Return of the Sea Legend" (Возвращение морской легенды, v1.06)** runs on a modern, readable engine. The approach is OpenMW-style:
**the original game scripts (Storm Script, `PROGRAM/*.c`) are kept unchanged and interpreted**; only the engine (the C++ part) is rewritten.
The game must be playable **in Ukrainian** (translation layer, see below). The owner speaks Ukrainian; answer in Ukrainian unless asked otherwise.

## First steps of every session
1. Read `docs/HANDOFF.md` (where work stopped).
2. **Code navigation goes through the graph first.** If `graphify-out/graph.json` exists, read `graphify-out/GRAPH_REPORT.md` once (god nodes,
   communities), and for any question about code (who calls X, where Y lives, how A reaches B) run `graphify query "<question>" --budget 1500`,
   `graphify path "A" "B"` or `graphify explain "Symbol"` **before** grepping or opening files; then open only the files it points to
   (`src=... loc=L..`). Grep is for exact strings and the original scripts (they are not in the graph). After changing code run `graphify update .`
   (seconds, no tokens) so the next session sees the new code. If `graphify-out/` is missing, see "Code graph" below.

## Hard rules
1. **Never modify the original game files** (everything one level above this folder: `PROGRAM`, `RESOURCE`, `stormex2.dll`, ...). All work lives in `port/`.
2. **Ask before downloading anything** (name, source, size). Pip packages/models were approved once for the translation tools; nothing else.
3. The addon's scripts are **inside `stormex2.dll`** (zlib overlay). `port/addon/merged/PROGRAM` = base `PROGRAM` overlaid with the unpacked addon files; Godot runs
   this merged tree (git-ignored, regenerate with `tools/unpack_stormex2.py` + `tools/merge_addon.py`).
4. `#define` names are **case-sensitive**, variable/function/keyword names are case-insensitive. Do not "fix" this (see `docs/vm_semantics.md`).
5. Windows + Git Bash/PowerShell. **Do not write C#/Python with backslashes through shell heredocs** (they get mangled): use the Write/Edit tools, or write a
   script file first. Verify every patch applied (many silent failures happened).
6. Commit style: small commits, English messages, trailer `Co-Authored-By: ...` as instructed by the harness. Do not push: the owner pushes himself.

**`docs/STATUS.md`** = what is interpreted / native / re-implemented / approximated, with accuracy ratings (generated by `python tools/status.py` from `docs/status_data.txt`; update the data file when a subsystem changes).
Read **`docs/ARCHITECTURE.md`** next: how script ↔ engine communication works and where each engine class lives.

**Code graph (graphify, git-ignored, local only)**: `graphify-out/graph.json` = AST graph of the C#/Python/PowerShell code (no docs or images).
To find callers, owners or paths between classes ask it first: `graphify query "<question>" --budget 1500`, `graphify path "A" "B"`,
`graphify explain "Symbol"`; overview: `graphify-out/GRAPH_REPORT.md`, `graphify-out/graph.html`. After code changes refresh it with
`graphify update .` (AST only, no tokens). If `graphify-out/` is missing (fresh clone) it can be rebuilt with the `graphifyy` pip package limited to code,
but that is a download: **ask the owner first** (hard rule 2).

## Build / run / test
```powershell
./run_game.ps1                      # builds game/SeaDogs.csproj and starts Godot with the project
```
Godot executable: `godot/Godot_v4.7.2-stable_mono_win64/Godot_v4.7.2-stable_mono_win64.exe --path game -- <user args>`.
Build only: `dotnet build game/SeaDogs.csproj -nologo -v q` (must print `0 Error(s)`).

**Automated regression tests (do not rely on playing by hand).** Owner's rule: after a small change run the build + one targeted check
(the scenario of the touched area); run the full suite (`-Smoke -Sea -Contracts`) once per batch of changes, not after every edit:
```powershell
powershell -ExecutionPolicy Bypass -File run_tests.ps1           # unit tests + game build (seconds)
powershell -ExecutionPolicy Bypass -File run_tests.ps1 -Smoke    # + Godot main-menu run, fails on [errors]/[unresolved]/exceptions
powershell -ExecutionPolicy Bypass -File run_tests.ps1 -Intro    # + intro into the first location (~3 min)
```
`StormScript.Tests/` (xunit, works offline from the local NuGet cache): `InterpreterTests` (VM semantics, one tiny script per rule —
**add a test for every interpreter bug you fix**), `ScriptCorpusTests` (all 1139 original scripts parse, ≤12 known defects; the game boots headless with
0 runtime errors / 0 unresolved functions), `FormatTests` (.ptc/.gm readers, path finding), `LanguageTests` (translation overlay), `GroupRelationsTests` (relations/alarms/attacker memory of CharactersGroups: the Godot-free core `StormScript/Runtime/GroupRelations.cs`), `CharacterMathTests` (turning, step sound alias, saved position text: `CharacterMath.cs`).
Tests needing game data return early if `addon/merged/PROGRAM` or the game folder is missing. The target selection of `GroupsState` and `Characters` live in the Godot project and
are only covered by the smoke runs.

**Test windows**: the owner wants to WATCH runs, so start Godot for tests with `--position 320,180 --resolution 1280x720` (before the `--`); `run_tests.ps1` does this, `-Hidden` moves the window off-screen (9000,9000) if they complain about pop-ups. Do not use `--headless` for screenshots (no rendering).

**Manual test hooks** (`--click`, `--mouse`, `--ctl`, `--goto`, `--call`, `--shot`, sea/map/land hooks, the sea test recipe) and the `SEADOGS_*` debug
env vars: **`docs/TESTING.md`**. Read it before writing a scenario or a manual run.
At screenshot time the log lists: `[errors]` (runtime errors), `[unresolved]` (engine functions the scripts call that do not exist), `[events]`, `[nohandler]`
(SendMessage to engine classes without a handler), `[chars]`, entities alive. **This is the main debugging instrument.**

**Fast loop**: play to a point once, save with `--ctl=Quick_Save@N`, then start tests with `--ctl=Quick_Load@200` (seconds instead of a minute).
Intro reference run (from the main menu to the first location, ~9000 frames):
`--click=B_NEWGAME@200 --click=RUNGAME@400 --answer=1@2700 --answer=1@2800 ... (13 answers, every 100 frames)`.

## Engine contract audit (automatic)
`python tools/contract_audit.py` (or `run_tests.ps1 -Contracts`, after the smoke runs so it sees fresh logs; ~10 s, stdlib only, always exits 0) writes
**`docs/CONTRACTS.md`** (tables sorted by player visibility) and `docs/contracts.json`: what the scripts expect from the engine vs what the port does —
native functions (missing / stubs / arity), entity classes (`EntityHandlers`), every `SendMessage` code/sub-command per target class (static closure of
the C# handler + `[nohandler]` from the logs, and whether the original `ProcessMessage` in `reference/storm-engine` handles it), engine-raised events
(`FireEvent`/`PostEventInternal`, interface ini `event:`) and their `GetEventData()` order/types vs the arguments the port passes and the reference
`core.Event` format, resources not found in the logs, ini files/sections never read. Use it to pick the next gap; check an entry in the code before
acting (known limitations are listed at the top of the report). Re-run it after implementing a contract.

## Original engine source (reference)
`reference/storm-engine` (git-ignored, approved shallow clone of https://github.com/storm-devs/storm-engine) is the open-sourced Storm Engine (a later
version of the same engine). **Before guessing any engine behaviour, look it up there**: `src/libs/<class>` (ship, sea_ai, sail/rigging, particles,
battle_interface, worldmap, location, xinterface, sound_service, tornado, sea_foam, sink_effect, ...). Differences to PotC are possible: the scripts of
this game remain the specification; use the C++ for formulas, constants, timings, message formats and event argument orders.

## Working method that paid off
* Scripts are the specification. To implement an engine class, grep the scripts for `SendMessage(&Obj, "fmt", MSG_...)`, the `#define`d message numbers
  (`messages.h`) and the events the engine must raise (`GetEventData()` order in the handlers). Never guess a contract before reading its script users.
* Run, read `[unresolved]`/`[nohandler]`/`[errors]`, fix the top entry, repeat. Compare with screenshots (Read the PNG).
* Silent semantic bugs in the interpreter were the costliest (see "Pitfalls" in `docs/ARCHITECTURE.md`). When a script flow "does nothing", trace it with
  `SEADOGS_TRACE` before suspecting the engine class.
